## 1. Data Pipeline

### Выбранный подход: ETL

Для проекта выбран подход **ETL (Extract -> Transform -> Load)**.

### Почему ETL, а не ELT

- Источник данных один: большой CSV-файл из Kaggle (`Russia Real Estate 2021`, 11.3+ млн объявлений, ~891 MB).
- Данные приходят в "сыром" виде и содержат дубликаты, ошибки ввода, пропуски и выбросы.
- Проект работает в локальной файловой среде и на учебной инфраструктуре, а не поверх полноценного DWH.
- Для дальнейшего обучения моделей и экономии RAM удобнее сначала очистить данные, а уже потом сохранять их в компактный аналитический слой (`Parquet`).

Таким образом, ETL лучше соответствует существующему коду проекта и ограничениям по инфраструктуре.

### Этапы пайплайна

1. **Extract**
   - Загрузка датасета из Kaggle через `src/data/download.py`.
   - Сырой слой хранится как CSV (`data/raw/all_v2.csv`).

2. **Raw Validation**
   - Проверка схемы и базовых ограничений через `src/data/contract.py`.
   - Цель этапа: зафиксировать качество источника до очистки, а не блокировать пайплайн из-за ожидаемых проблем исходного датасета.

3. **Transform / Clean**
   - Нормализация имен полей: `id_region -> region`, `level -> floor`, `levels -> total_floors`.
   - Удаление полных дубликатов.
   - Фильтрация аномальных значений по цене и площади.
   - Базовое заполнение пропусков по `kitchen_area`, `geo_lat`, `geo_lon`.
   - Реализовано в `src/data/clean.py`.

4. **Clean Validation**
   - Повторная валидация уже очищенного слоя.
   - Цель: убедиться, что данные готовы к построению признаков и моделированию.

5. **Feature Engineering**
   - Формирование базовых и производных признаков.
   - Исключение признаков с высоким риском leakage.
   - Реализовано в `src/data/features.py`.

6. **Sampling**
   - Для эффективной работы используется стратифицированное семплирование по регионам.
   - Это позволяет уменьшить объем modeling-датасета без полного разрушения географического распределения.

7. **Train / Validation / Test Split**
   - Разделение выборки на `train`, `validation`, `test`.
   - Сплит делается воспроизводимо и с учетом `region`, если это возможно.

8. **Load**
   - Артефакты сохраняются в `data/processed/` в формате `Parquet`.
   - Основной orchestration реализован в `src/data/pipeline.py`.

### Выбранные инструменты

- **pandas**: основной инструмент табличной обработки и очистки данных.
- **pyarrow**: запись артефактов в формате `Parquet`.
- **scikit-learn**: разбиение на train/validation/test.
- **Parquet**: компактное и быстрое хранение обработанных данных.

### Почему этот стек подходит проекту

- Он уже согласован с существующим кодом и зависимостями.
- Он достаточно прост для учебного проекта, но при этом промышленно применим.
- Он позволяет перейти от EDA к воспроизводимому data pipeline без избыточной инфраструктуры вроде Spark/Airflow.

### Data Pipeline Flow

```text
Kaggle CSV
   |
   v
Download Script
   |
   v
Raw Validation
   |

Cleaning / Normalization
   |

```

## 2. Feature Engineering

### Источники признаков

Все признаки строятся из одного источника данных: `Russia Real Estate 2021`.

Базовые поля из raw/clean слоя:

- `region`
- `object_type`
- `building_type`
- `rooms`
- `area`
- `kitchen_area`
- `floor`
- `total_floors`
- `geo_lat`
- `geo_lon`

### Производные признаки

В рамках Checkpoint 2 добавлены следующие инженерные признаки:

- `is_studio`
- `log_area`
- `has_kitchen_area`
- `kitchen_to_area_ratio`
- `floor_ratio`
- `is_top_floor`
- `is_first_floor`
- `region_listing_count`
- `region_median_area`

### Признаки, исключенные из моделирования

Следующие поля не используются как modeling features:

- `house_id`
- `street_id`
- `postal_code`

Причина: высокий риск location leakage и переобучения на уровне адреса/микрорайона.

### Окна агрегации

У датасета отсутствует операционная временная ось для online-обновлений: это статический срез рынка за 2021 год.

Поэтому в проекте используются не rolling windows, а **snapshot aggregations**:

- агрегации считаются на актуальном snapshot очищенных данных;
- recompute выполняется при каждом запуске pipeline;
- в online-сценарии используются только признаки, вычислимые из request без тяжелых пересчетов.

### Частота обновления признаков

- **Raw data**: не обновляется регулярно, источник статический.
- **Offline features**: пересчитываются при каждом запуске ETL pipeline.
- **Online features**: вычисляются на лету из входных параметров пользователя.

### Концепция Feature Store

Для проекта выбран практический, а не инфраструктурно тяжелый подход к Feature Store.

#### Offline Feature Store

Роль offline store выполняют артефакты в `Parquet`:

- `clean.parquet`
- `features_offline.parquet`
- `train.parquet`
- `val.parquet`
- `test.parquet`

Этот слой используется для экспериментов, обучения моделей и воспроизводимости.

#### Online Features

Online-признаки формируются в inference-time из пользовательского ввода и простых детерминированных преобразований:

- `is_studio`
- `log_area`
- `has_kitchen_area`
- `kitchen_to_area_ratio`

Такие признаки не требуют отдельного online-хранилища и хорошо подходят для MVP.

#### Feature Registry

В проект добавлен реестр признаков:

- кодовая версия: `src/data/features.py`
- документированная версия: `docs/feature_registry.md`

Реестр хранит:

- имя признака;
- источник;
- тип;
- доступность (`offline`, `online`, `offline+online`, `excluded`);
- частоту обновления;
- описание;
- риск leakage.

## 3. Работа с данными

### Выбранный подход: семплирование

Для проекта выбран подход **sampling**, так как:

- исходный датасет очень большой;
- обучение на полном объеме на учебной инфраструктуре неэффективно;
- на раннем этапе важнее воспроизводимость и скорость итераций, чем абсолютный охват всех записей.

### Почему именно stratified sampling по регионам

- рынок недвижимости сильно неоднороден по регионам;
- простое случайное семплирование может исказить долю малых регионов;
- регион является одним из ключевых факторов стоимости и важной осью стратификации.

### Практическая стратегия

- полный cleaned dataset сохраняется как базовый артефакт;
- для modeling-слоя формируется sample ограниченного размера;
- семпл строится пропорционально региональному распределению с минимальным порогом по числу записей на регион;
- затем sample делится на `train / val / test`.

### Бизнес- и инженерный эффект

- пайплайн укладывается в ограничения по RAM;
- ускоряется обучение baseline и будущих моделей;
- результаты по регионам становятся более стабильными и интерпретируемыми.

## 4. DFD (Data Flow Diagram)

```text
[Kaggle Russia Real Estate 2021]
              |
              v
      [Download Script]
              |
              v
        [Raw CSV Layer]
              |
              v
   [Schema / Contract Validation]
              |
              v
       [Cleaning & Normalization]
              |
              v
      [Clean Parquet Dataset]
              |
              v
      [Feature Engineering Layer]
              |
              v
 [Sampled Modeling Dataset Builder]
              |
              v
   [Train / Validation / Test Sets]
              |
              v
   [Offline Feature Store / Artifacts]
              |
              +--------------------+
              |                    |
              v                    v
      [Model Training]      [FastAPI Inference]
                                     |
                                     v
                              [Streamlit UI]
```

### Интерпретация DFD

- DFD показывает движение данных от Kaggle-источника до слоя инференса.
- Важное отличие от architecture diagram: здесь акцент сделан на жизненный цикл данных, а не на сервисные компоненты.
- Такой формат удобен для объяснения, где именно происходят проверки качества, очистка, построение признаков и формирование train/test артефактов.
